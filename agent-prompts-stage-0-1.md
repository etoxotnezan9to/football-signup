# Промпты для ИИ-агентов: этапы 0 и 1

Как пользоваться: каждый промпт отдаётся отдельному агенту целиком, вместе с блоком «Общий контекст». Следующий этап начинается только после того, как вы проверили критерии приёмки предыдущего.

Порядок: 0 → 1a → 1b. Этап 0 можно вести параллельно с 1a.

---

## Общий контекст (вставлять в начало каждого промпта)

Проект: VK Mini App «Запись на футбол». Сейчас записи на игру идут плюсами в групповом чате ВКонтакте, организатор вручную публикует обновлённый список. Нужно заменить это приложением.

Функции:
1. Любой пользователь может стать организатором, создав игру.
2. Любой пользователь видит список созданных игр и записывается на игру кнопкой «+» с выбором числа мест.
3. Список записавшихся обновляется у всех пользователей в реальном времени.

Принятые решения (не пересматривать без запроса к владельцу):
- VK app ID: 54809461. Секретный ключ приложения (`VK_APP_SECRET`) передаётся только через переменные окружения, в репозиторий и в логи не попадает.
- Платформа одна: VK Mini App. VK Tunnel недоступен (отключён VK), не использовать.
- Оплата ручная: организатор сам отмечает «оплачено». Приложение деньги не принимает и не возвращает.
- Лимит: не более 5 мест на одного пользователя в одной игре суммарно (основной состав и очередь вместе). Значение хранится константой `MAX_SEATS_PER_USER = 5` в общем пакете.
- Если мест не хватает, запись делится: например, при 2 свободных местах «+3» даёт 2 места в составе и 1 в очереди.
- Очередь FIFO по времени записи. При освобождении мест очередь продвигается автоматически.
- Стек: монорепозиторий (pnpm), TypeScript strict, React + VKUI + `@vkontakte/vk-bridge` + Vite (фронтенд), Node.js 22 + Fastify (бэкенд), SQLite (WAL-режим) вместо PostgreSQL, WebSocket для обновлений, Vitest, Playwright.
- Авторизация: проверка подписи стартовых параметров VK (`sign`, HMAC-SHA256 с секретным ключом приложения), без паролей.
- Домен: `etoxotnezan9to.ru`. Планируемые поддомены: `football.etoxotnezan9to.ru` (production), `football-test.etoxotnezan9to.ru` (staging). A-записи на `83.217.211.234` создаёт владелец.

Правила работы агента:
- Сначала прочитай `AGENTS.md` и `docs/`, если они есть. Если ты меняешь соглашения или команды, обнови `AGENTS.md`.
- Работай в отдельной ветке и в конце подготовь описание PR.
- Не придумывай требований, которых нет в этом документе и в спецификации. Если не хватает данных, перечисли вопросы в отчёте и сделай разумное допущение, пометив его.
- Секреты, ключи и пароли не пишем в код, примеры конфигов, логи и сообщения. Только `.env.example` с пустыми значениями.
- Формат отчёта в конце: что сделано, что не сделано, принятые допущения, как проверить, открытые вопросы.

## Промпт 0. Спецификация и контракты

**Цель:** зафиксировать решения, чтобы дальше агенты не додумывали.

**Входные данные:** блок «Общий контекст».

**Результат (файлы в `docs/`):**
1. `spec.md`:
   - сущности `User` (vk_id, имя, фамилия, ссылка на аватар), `Game` (организатор, название, дата и время начала, площадка, адрес, формат (текст), взнос в рублях, вместимость (число мест в составе), описание, реквизиты для предоплаты (текст), контакт организатора для чека (ссылка VK или телефон), статус `active`/`cancelled`/`finished`), `Signup` (game_id, user_id, seats, created_at, updated_at, paid (число оплаченных мест, 0..seats));
   - пользовательские сценарии: создание игры, просмотр списка, запись и изменение числа мест, отмена записи, редактирование и отмена игры организатором, отметка оплаты, удаление участника организатором;
   - правила очереди (пример из контекста, порядок продвижения, что происходит при уменьшении и увеличении числа мест, что с записью при уменьшении вместимости игры организатором);
   - права доступа (таблица «действие → кто может»);
   - ошибки и коды (превышен лимит 5, игра отменена или прошла, мест для изменения нет, нет прав);
   - экраны и состояния фронтенда (список, игра, форма, мои игры) в виде текстового описания, без макетов;
   - нефункциональные требования: данные обновляются у всех в течение 2 секунд, одновременные записи не приводят к превышению вместимости.
2. `openapi.yaml`: REST-контракт всех эндпоинтов (`POST/GET /games`, `GET/PATCH /games/:id`, `POST /games/:id/cancel`, `PUT/DELETE /games/:id/signup`, `PATCH/DELETE /games/:id/signups/:signupId`, `GET /me/games`), схемы запросов и ответов, ошибки. Префикс `/api`.
3. `realtime.md`: протокол WebSocket на `/ws` (авторизация, подписка на игру и на общий список, события `game.created`, `game.updated`, `roster.updated`, формат сообщений, heartbeat, правила переподключения и догрузки).
4. `db-schema.md`: схема SQLite (таблицы, индексы, ограничения), правила конкурентной записи (транзакции `BEGIN IMMEDIATE`, единственный процесс API), политика миграций.
5. Приложение к `spec.md`: функция формирования текстового списка в привычном виде («1-6) Имя (6) ✅оплачено», «В очереди: …») для кнопки «Скопировать список».

**Ограничения:** кода приложения не писать. Все числовые лимиты вынести в раздел «Константы».

**Критерии приёмки:**
- Для каждого пункта из «Функции» есть эндпоинт и экран.
- `openapi.yaml` проходит валидацию (`redocly lint` или аналог).
- В документах нет противоречий и фраз «на усмотрение разработчика».
- Приложены минимум 10 примеров очереди «было → действие → стало» для тестов этапа 3.

## Промпт 1a. Каркас репозитория и CI (без доступа к серверу)

**Цель:** рабочий монорепозиторий с проверками и сборкой образов.

**Входные данные:** блок «Общий контекст», результаты этапа 0 (если уже готовы; иначе делай каркас без доменной логики).

**Задачи:**
1. Структура: `apps/web` (Vite + React + TS + VKUI), `apps/api` (Fastify + TS), `packages/shared` (общие типы, константа `MAX_SEATS_PER_USER`, схемы zod), `docs/`, `deploy/`.
2. Единые настройки: pnpm workspaces, TypeScript strict, ESLint, Prettier, Vitest во всех пакетах, команды в корне: `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`.
3. `apps/api`: минимальный сервер с эндпоинтом `GET /api/health` (версия, время), конфигурация через переменные окружения с валидацией (`PORT`, `DATABASE_FILE`, `VK_APP_ID`, `VK_APP_SECRET`, `NODE_ENV`), структурные логи без секретов. Подключение SQLite (WAL) и механизм миграций (простые SQL-файлы в `apps/api/migrations`, применяются при старте), пустая первая миграция.
4. `apps/web`: стартовая страница, которая инициализирует `vk-bridge`, показывает имя пользователя из `VKWebAppGetUserInfo` и состояние соединения. Режим разработки с мок-параметрами VK (флаг `VITE_MOCK_VK=1`, выбор тестового пользователя). Не использовать VK Tunnel.
5. Docker: `apps/api/Dockerfile` (multi-stage, Node 22 alpine, непривилегированный пользователь, данные SQLite в томе `/data`), `.dockerignore`.
6. GitHub Actions:
   - `ci.yml`: на каждый PR — install (кэш pnpm), lint, typecheck, test, build.
   - `deploy.yml`: на пуш в `develop` собирает образ API и статику веб-приложения, публикует образ в GHCR (`ghcr.io/<owner>/football-api:<sha>` и `:staging`), артефакт статики — архив. Шаг выкладки на сервер оформить как отдельный job, который пока выключен условием и читает секреты `DEPLOY_HOST`, `DEPLOY_PORT`, `DEPLOY_USER`, `DEPLOY_SSH_KEY` (реализация этого job — в этапе 1b).
7. `AGENTS.md` в корне: стек, структура, команды, соглашения (именование, коммиты, где лежат контракты), режимы разработки (браузер с моками; проверка внутри VK только на staging), запрет на секреты в репозитории.
8. `.env.example` в корне и в `apps/*`, README с кратким запуском.

**Ограничения:** не подключаться к серверу, не просить секреты. Бизнес-логику (игры, записи) не реализовывать.

**Критерии приёмки:**
- На чистой машине `pnpm install && pnpm lint && pnpm typecheck && pnpm test && pnpm build` проходят.
- `docker build` образа API проходит, контейнер стартует, `GET /api/health` отвечает 200, миграции применяются, том `/data` сохраняется между перезапусками.
- Веб-приложение открывается в браузере в режиме моков и показывает тестового пользователя.
- CI зелёный на PR.

## Промпт 1b. Сервер: окружения staging и production

**Цель:** подготовить сервер так, чтобы приложение открывалось внутри VK по HTTPS. Этот этап выполняет агент с доступом к серверу по SSH (или вы вручную по его инструкции). Секреты агенту в чат не передаются.

**Входные данные:** блок «Общий контекст», результат этапа 1a (образ API, статика, `deploy.yml`), доступ по SSH, выданный владельцем.

**Сведения о сервере:**
- Ubuntu 24.04, 2 vCPU, около 2 ГБ RAM (свободно около 1,4 ГБ), диск около 14 ГБ свободно.
- SSH на порту 10022, вход под root. Установлены Docker и nginx. Node есть только через nvm у root, для приложения не используем. Caddy и PostgreSQL нет и не нужны.
- nginx слушает порт 80, порт 443 свободен. На сервере работают посторонние сервисы (порты 8443, 2096, 1945 и другие): их не трогать, наши порты выбирать после проверки `ss -tlnp`. Старые настройки nginx сначала сохранить копией, существующие конфиги не удалять без согласования, хотя владелец сказал, что в них нет ничего важного.

**Задачи:**
1. Сначала только чтение: прочитать `nginx -T`, `docker ps`, `ss -tlnp`, свободную память и диск. Показать владельцу, что будет изменено, и получить подтверждение перед любыми изменениями.
2. Подготовить `deploy/server-setup.sh` (идемпотентный, с комментариями), а не выполнять разовые команды вручную. Скрипт:
   - создаёт пользователя `deploy` (без пароля, вход по ключу, членство в группе `docker`), каталоги `/opt/football/{staging,prod}` и `/var/www/football/{staging,prod}`;
   - добавляет в `authorized_keys` пользователя `deploy` публичный ключ, который передаётся аргументом (приватный ключ создаёт и хранит владелец, в GitHub Secrets);
   - ставит certbot и плагин для nginx, выпускает сертификаты для `football.etoxotnezan9to.ru` и `football-test.etoxotnezan9to.ru`, проверяет автопродление;
   - добавляет отдельные конфиги nginx `/etc/nginx/conf.d/football-staging.conf` и `football-prod.conf`: HTTPS, редирект с 80, статика из `/var/www/football/<env>`, SPA-fallback, прокси `/api` и `/ws` на `127.0.0.1:<порт>` (WebSocket с `Upgrade`, увеличенный `proxy_read_timeout`), заголовки безопасности, совместимые с открытием в iframe VK (не ставить `X-Frame-Options: DENY`, использовать `Content-Security-Policy: frame-ancestors` с разрешением VK-доменов);
   - перед перезагрузкой nginx выполняет `nginx -t`, при ошибке откатывает.
3. `deploy/docker-compose.staging.yml` и `deploy/docker-compose.prod.yml`: контейнер API с лимитом памяти (около 300 МБ), `restart: unless-stopped`, порт публикуется только на `127.0.0.1` (разные порты для staging и production, выбранные свободными), том для SQLite, healthcheck по `/api/health`, переменные окружения из файла `/opt/football/<env>/.env` (владелец заполняет сам, права `600`).
4. Job выкладки в `deploy.yml` включить: подключение по SSH под `deploy`, скачивание образа из GHCR, распаковка статики в `/var/www/football/<env>`, `docker compose up -d`, проверка `/api/health` снаружи по HTTPS, откат к предыдущему образу при неудаче. Если репозиторий приватный, на сервере нужен `docker login ghcr.io` с токеном только для чтения (токен вводит владелец сам).
5. Бэкапы: `deploy/backup.sh` (консистентный дамп SQLite через `sqlite3 .backup` или `VACUUM INTO`, сжатие, ротация 14 копий) и cron-задача раз в сутки; в README описать восстановление и как забирать копии за пределы сервера.
6. Документ `docs/runbook.md`: как выкатить, откатить, посмотреть логи, продлить сертификат, восстановить из бэкапа.
7. Рекомендации по безопасности (выполнять только после подтверждения владельца): включить вход по ключам для `deploy`, после проверки отключить вход под root по паролю, настроить `ufw` так, чтобы остались открытыми порт SSH 10022, 80, 443 и порты существующих сервисов, которыми владелец пользуется.
8. В кабинете VK указать адрес staging как адрес разработческой версии приложения (шаг для владельца, оформить как короткую инструкцию в `docs/runbook.md`).

**Ограничения:** не открывать порты контейнеров наружу, не хранить секреты в репозитории, не менять чужие сервисы, ничего не удалять без подтверждения.

**Критерии приёмки:**
- `https://football-test.etoxotnezan9to.ru` открывается с валидным сертификатом, `/api/health` отвечает 200.
- Пуш в `develop` приводит к обновлению staging без ручных действий; неудачный деплой откатывается.
- WebSocket-соединение через nginx проходит (проверка простым клиентом).
- Резервная копия создаётся и восстанавливается на тестовом файле.
- После перезагрузки сервера контейнеры поднимаются сами.
- Приложение (стартовая страница из этапа 1a) открывается внутри VK у администратора приложения и показывает его имя.
